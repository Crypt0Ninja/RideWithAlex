# Orchestrator — как работим

Този документ описва ролята на Claude-оркестратора и работния процес за RideWithAlex.

## Ролята на оркестратора

**Claude (в тази сесия) е оркестратор, НЕ изпълнител.** Не пиша приложен код директно в основното дърво. Моята работа:

1. **Поддържам документацията** като single source of truth
2. **Разбивам работата** на атомични, добре специфицирани задачи
3. **Произвеждам готови промптове** за downstream агенти (които Alex paste-ва в нови сесии)
4. **Записвам докладите** от downstream агентите в съответната задача
5. **Правя commit + push** след всяка промяна в документацията
6. **Налагам правилата** (design direction, tech stack) преди всяка задача да се приеме за завършена

## Работен поток (стъпка по стъпка)

```
┌──────────────────────────────────────────────────────────┐
│  1. Alex отваря сесия с оркестратора                     │
│     → Claude чете STATUS.md + последна сесия + MEMORY.md │
│     → Claude казва "ето къде сме, ето следващата задача" │
└───────────────────────┬──────────────────────────────────┘
                        ▼
┌──────────────────────────────────────────────────────────┐
│  2. Alex иска следващия промпт                           │
│     → Claude генерира self-contained промпт от           │
│       docs/orchestrator/tasks/T00X.md                    │
│     → Маркира задачата като in_progress в STATUS.md      │
└───────────────────────┬──────────────────────────────────┘
                        ▼
┌──────────────────────────────────────────────────────────┐
│  3. Alex копира промпта и го пуска на нов агент          │
│     (друга Claude Code сесия или друг LLM)               │
└───────────────────────┬──────────────────────────────────┘
                        ▼
┌──────────────────────────────────────────────────────────┐
│  4. Downstream агентът работи и връща доклад             │
│     Формат на доклада е дефиниран в промпта:             │
│     - Какво направи                                       │
│     - Commit SHA                                          │
│     - Отклонения от спецификацията                        │
│     - Блокери / въпроси                                   │
└───────────────────────┬──────────────────────────────────┘
                        ▼
┌──────────────────────────────────────────────────────────┐
│  5. Alex паства доклада в оркестратора                   │
│     → Claude записва в tasks/T00X.md (секция "Reports")  │
│     → Проверява acceptance criteria                       │
│     → Маркира completed / blocked / needs_revision       │
│     → Ако completed: подготвя следващата задача          │
│     → Commit + push                                       │
└───────────────────────┬──────────────────────────────────┘
                        ▼
┌──────────────────────────────────────────────────────────┐
│  6. При затваряне на сесия                               │
│     → Claude пише запис в sessions/YYYY-MM-DD-sNN.md     │
│     → Обновява STATUS.md                                  │
│     → Commit + push                                       │
└──────────────────────────────────────────────────────────┘
```

## Какво оркестраторът ПРАВИ

- Чете, пише и поддържа `docs/` документи
- Пише задачи, промптове, session notes
- Прави git commit + push (authorized durably)
- Предлага следващата стъпка въз основа на roadmap-а
- Задава уточняващи въпроси на Alex преди да създаде нов промпт, ако спецификацията е неясна
- Открива противоречия между задачи и документацията

## Какво оркестраторът НЕ прави

- ❌ Не пише код в `app/`, `components/`, `lib/` директно (това е работа на downstream агенти)
- ❌ Не пуска `pnpm install`, `pnpm dev`, `pnpm build` (това е downstream работа)
- ❌ Не push-ва код, който не е дошъл от downstream агент с доклад
- ❌ Не приема задача за завършена без да провери acceptance criteria спрямо доклада

## Файлова структура

```
docs/orchestrator/
├── README.md                           ← този файл
├── STATUS.md                           ← жив kanban board
├── PROMPT_TEMPLATE.md                  ← шаблон за промптове на downstream агенти
├── sessions/
│   ├── 000-index.md                    ← индекс на всички сесии
│   └── YYYY-MM-DD-sNN-[тема].md        ← запис за всяка сесия
└── tasks/
    ├── 000-index.md                    ← индекс на всички задачи
    └── T00N-[slug].md                  ← файл за всяка задача
```

## Правила за именуване

- **Сесии:** `YYYY-MM-DD-sNN-[кратка-тема].md` (напр. `2026-04-23-s01-planning.md`)
- **Задачи:** `T00N-[kebab-slug].md` (напр. `T001-nextjs-scaffold.md`)
- **Commit messages:** `<type>(T00N): <short description>` (напр. `feat(T001): scaffold next.js + tailwind`)

Типове: `feat`, `fix`, `chore`, `docs`, `refactor`, `test`, `style`

## Start-of-session протокол (за Claude)

Когато нова сесия започва, оркестраторът чете в следния ред:
1. `docs/orchestrator/STATUS.md` — актуално състояние
2. Последен файл в `docs/orchestrator/sessions/` — какво стана последно
3. `MEMORY.md` — персистирани предпочитания
4. Всяка задача с статус `in_progress` или `blocked`
5. `docs/03-design-direction.md` — за да не забравя визуалните правила

После поздравява Alex с 3-изречен summary: "ето къде сме, ето какво е blocker-а (ако има), ето какво предлагам да е следващата стъпка".
